## (a) Verdict: SPLIT FIRST

## (b) Findings

### F1 (blocking) S4 is a test gap, not a production bug; the spec's "decision" invites scope creep
Evidence: provider.go:860-861 (Observe) calls effectiveConfig + applyDerivations; correspondence.go applyDerivations has `sv, ok := state[d.From]; if !ok { continue }`. The production Observe ALREADY leaves isIpv6Enabled out when ipv6CidrBlocks is absent. Existing coverage: provider_test.go TestObserve:360-411 only the present case (`isIpv6Enabled == "true"`); observed_test.go:177 TestAPartialReadNeverFabricatesAValue goes through normalizeObserved, which deletes every non-`observed` field from EffectiveConfig after the fact (observed.go "a value that is not observed does not stay"), so deleting the guard in applyDerivations is masked there. So lemma 4 of the spec is plausible (not run). The spec text "Ezután dönts ... a production Observe használja-e a normalizeObserved védelmét" suggests a behaviour change that is not needed for the property.
Why it matters: wiring normalizeObserved into Observe would prune wrong-typed/absent fields from effective_config (content change, even without a new `coverage` field). The stop condition only covers the output "alakja" (shape). Content pruning is not a shape change in the strict sense but changes what Plan sees (see F2).
Change: replace the "Ezután dönts" sentence with: "S4 csak teszt: a production Observe-ot nem módosítod. A normalizeObserved bekötése (szűrés vagy coverage) külön tulajdonosi döntés; ha úgy látod, hogy a tulajdonság csak kódváltoztatással teljesülne, állj meg." Extend the stop condition: "ha az Observe effective_config TARTALMA (nem csak alakja) bármely, ma ok-ágon visszaadott mezőre változna".

### F2 (should-fix) S4 property is stated for the missing case only; a conscientious or lazy agent can satisfy it while losing information
Evidence: correspondence.go jsonNonEmpty returns false for "", "null", "[]", `""`, "{}", "0", "false". Fixture conformant/oci/response.json has `"ipv6CidrBlocks": []` for ipv6_enabled=false (real OCI shape per the vendored fixture), partial-read has the key absent. A "fix" that drops isIpv6Enabled whenever it would be false makes the new missing-case test pass and silently loses the real disabled state ([] -> false), which conformance then reads as unobserved.
Also unspecified: `"ipv6CidrBlocks": null` (jsonNonEmpty -> false, so today null yields observed false, while normalizeObserved's coverage rule for derived fields treats key-present as `observed`). The two paths agree today; the spec should pin that, not leave it to the agent.
Plan interaction (not in the spec): isIpv6Enabled is `x-cic-policy: input-only` (schemas/core/vcn.json), policyOp maps input-only -> replace (provider.go policyOp), Plan diffs `valueEqual(dv, observed[name])`. A partial read (key absent) with intent isIpv6Enabled=false therefore plans replace = DeleteVcn + CreateVcn. The existing guard produces this already. This is an existing hazard the S4 negative test will make visible; the spec says "do not worsen Plan" but never tells the agent to record it.
Change: add to S4 the required positive controls in the SAME test table: key absent -> isIpv6Enabled absent from effective_config AND state unchanged; `[]` -> `false`; non-empty -> `true`; `null` -> record actual behaviour and say whether it is intended. Add: "Rögzítsd a jelentésben, mit tervez a Plan, ha a desired isIpv6Enabled=false és az observed hiányzó (várható: replace, input-only); NE változtasd a Plan-t, csak nevesítsd mint nyitott kockázatot."

### F3 (blocking) committed module.wasm / project.yaml / MANIFEST are not addressed
Evidence: module/module.wasm is tracked (MANIFEST.sha256:89) and project.yaml metadata.buildHash (project.yaml:41) equals its sha256; `make wasm.build` (mk/wasm.mk) rewrites BOTH module.wasm and project.yaml (`wasm.buildhash`). module_loadtest_test.go:33 `const wasmPath = "module.wasm"` reads the committed binary. Consequences: (1) a test "through the real Call export" that uses `wasmPath` as is runs the OLD committed binary, so it cannot see S3 and fails, or the agent works around it; (2) running `make wasm.build` in the feature clone modifies module.wasm + project.yaml + MANIFEST (project.yaml is the signed declaration); (3) the spec's bit-identical list (input.md "Ellenőrizhető elvárások" 4) names go.mod/go.sum, CI, schema, pins, Relay, manual_real_oci_test.go but not project.yaml/module.wasm; Q9 only says regenerate MANIFEST.
Change (S5/S6, Q8/Q9 and elvárás 4): "A module.wasm-ot és a project.yaml-t NEM módosítod és nem commitolod. A Call-exporton átmenő tesztekhez a guestet eldobható helyre fordítod (`tinygo build -o <scratch>/module.wasm -target wasip1 -scheduler=none .` a builder image-ében), és az ÚJ teszt ezt az utat olvassa (pl. env változó); a meglévő `wasmPath`-os tesztek érintetlenek. A módosított guest hash-e kerüljön a jelentésbe. Add hozzá az elvárások 4. pontjához: module/module.wasm, project.yaml bit-azonos." State explicitly that the committed artifact becomes stale relative to the source until the owner rebuilds/re-signs (owner decision).

### F4 (blocking) S3: result location, step scoping and error channel are underspecified; wrong choices break existing tests
Evidence:
- executionResult (provider.go ~Execute section) = {status, steps[]}; executionStep has no resource_id; there is no `provider_metadata` on the result. provider-abi.md:96-103 shows `execution-result {status, job, provider_metadata{...resource_id}, evidence}` under "Request/response shapes (informative)"; the code already diverges from that shape (steps instead of job/provider_metadata/evidence, and poll returns pollResult not execution-result: provider-abi.md:17-20 vs provider.go pollResult). manual-verification.md:223 and manual_real_oci_test.go:452,608-620 consume `steps[].work_request_id` and `steps[0].Operation`. So "provider_metadata.resource_id" is a design choice (per-step `resource_id`, vs new top-level `provider_metadata` mirroring the doc and the existing `provMeta` type used by observe), not a spec fact. A replace plan has [Delete, Create] steps, so top-level vs per-step matters.
- Scope: executeOne is shared by create/update/action/delete ops. Existing tests return `{}` or empty bodies on 2xx for UpdateVcn (module_loadtest_test.go:~345 body `{}`, provider_test.go TestExecuteAsyncAndBasePath 202 with no body). If the "2xx without id -> typed error" rule is applied to all ops, existing tests break, and the spec says they must stay unchanged. The rule must be limited to `role == create`.
- Error channel: today a failed step is NOT errResult; it is `result.Status="failed"` + step.Error/ErrorClass (provider.go executeOne; manual-verification.md:71 "step-level, result.status: failed"). The spec says "tipizált hiba" without saying which channel.
- Danger case: 2xx create with unusable id means the VCN WAS created at OCI. "Typed error" must say created-but-id-unknown, not look like a failed create (retry creates a duplicate; there is an idempotency-token requirement in provider-abi.md "execution_policy").
- OCID shape check is undefined: existing fixtures use `ocid1.vcn..z` (provider_test.go) and `ocid1.vcn.oc1..xyz`; the spec says only "OCID-alakú".
Change: S3 -> "A resource_id a steps[i] elemen él (`resource_id`, omitempty), csak role=create lépésnél; a meglévő mezők neve/tagje változatlan. Hibakezelés: result.status=failed, a lépés error_class/error mezőivel (nem errResult); az üzenet mondja ki, hogy a hívás 2xx volt, az erőforrás létrejöhetett, az azonosítója ismeretlen. OCID-alak: `ocid1.vcn.` prefix + nem üres maradék (a meglévő fixture-ök `ocid1.vcn..z` alakját elfogadja). Update/action/delete lépésekre a viselkedés változatlan (a meglévő tesztek `{}` törzzsel zöldek maradnak)." Alternatively state that the owner decides top-level vs per-step and list it in Határjelzés.

### F5 (should-fix) S3 ABI compatibility is mostly fine, but the spec does not ask for the compatibility checks that matter
Evidence: abi.schema.yaml covers only project.yaml's `abi:` block (exports, operations, imports), not payload bodies; capability-manifest.schema.yaml not touched by a result field; no DisallowUnknownFields anywhere in module/ (git grep at 04c2482: none); Relay 55a899f has no consumer of the execute result (git grep for provider_metadata / work_request_id / resource_id in *.go: no hits; the `steps` hits are ProofTrace types unrelated). abi_manifest_test.go checks only module.wasm exports. So an `omitempty` additive field is JSON-compatible and breaks no schema file. What the spec should ask: (1) a golden/regression assertion that the pre-existing JSON for a non-create execute result is byte-identical before/after (omitempty proof); (2) manual_real_oci_test.go (build tag manual_real_oci, uses executionResult.Steps) still compiles: `go vet -tags manual_real_oci ./...` without running it; (3) docs/design/specs/provider-abi.md updated to describe the real shape (module docs are in scope; MANIFEST/docs.link-check). Add these to S3 and Q-list. Note S3 changes the guest, so F3 applies.

### F6 (should-fix) S2 vs "no ABI change": the contradiction is real in packaging, not in text
Evidence: Határjelzés allows S1/S2 ABI work "ezen a jelzett kereten", S2 says PROPOSED + not mergeable; provider-abi.md already documents `binding: { provider, region, compartment_id }` (request shapes block), so the field is consistent with the documented direction. But: (a) one feature branch holds S2 with S3/S4, so the branch (and any later PR) cannot be merged until the owner decides M2; the spec never says to keep S2 in separate commits or a separate branch, and the owner's value is S3/S4; (b) execBinding is shared by observe/execute/destroy/invoke/poll requests (provider.go), so adding the field touches every op's request type; (c) renderBody (provider.go) already sends `compartmentId` from `config` for create (it copies every c.fields entry present in config, and compartmentId is the schema's only required config field: schemas/core/vcn.json). The spec does not say which wins when both config.compartmentId and binding.compartment_id exist and differ; nor that the validation applies only to create (update tests have no compartment); nor that `validate` (conformIntent requires compartmentId) would reject an S1 output that lacks it.
Change: move S2 code to its own job/branch (see table); define precedence ("ha mindkettő jelen van és eltér: tipizált validációs hiba, 0 OCI-kérés; ha csak a binding: abból; ha csak a config: a mai viselkedés marad, mert ezt a manual verification mérte"), scope to create, and the M2 record first.

### F7 (should-fix) S1: factual gaps in the mapping text
Evidence: registry 6db77d4 general/network/network-space/network-space.yaml: `secondary_cidr_blocks` is a collection with `item_fields: [{name: cidr, role: key}]`, i.e. a list of objects `{cidr: ...}`, whereas registry ac567ae correspondence `rest` yields cidrBlocks[1:] as strings. The spec says only "(az first/rest inverze)". The forward map must unwrap/wrap `{cidr}` items and must say so, otherwise the property test `előre(vissza(x))` is satisfied by a self-consistent but wrong convention. Also `vissza` (the inverse) does not exist in the module (it exists only in the registry's Python test correspondence), so the agent writes both directions -> the property test is partly tautological; require the golden vectors (Forms output) and the vendored observed.registry.json fixtures as the independent oracle, not the agent's own inverse.
Absent vs false: `ipv6_enabled`, `dns_label`, `tags`, `secondary_cidr_blocks` are optional with NO default (schema comments: "SZÁNDÉKOSAN NINCS default"), so Normalize does not inject them (this makes the spec's explicit rejection of dns_*_enabled safe: a defaulted value cannot trigger it). But the forward map can fabricate: absent ipv6_enabled must stay absent in the OCI body (not isIpv6Enabled:false), absent tags not `freeformTags:{}`. That is the S4 fabrication class on the write side and the spec is silent. cidr_block is "unevaluated" by Forms (real-schemas.json `unevaluated_contracts: $.cidr_block`) so CIDR validity is the module's job; the spec correctly lists it as a negative case but should require the same regex-level check be independent of Forms.
Also `AddVcnCidr` is an existing action op (schemas/core/vcn.json): secondary CIDRs could be added post-create; the spec maps them into CreateVcn.cidrBlocks without noting the choice. And `Validate` requires compartmentId in config (conformIntent), so S1 output fed to validate fails unless compartment is merged (F6).
Change: add the `{cidr}` item shape; add "hiányzó opcionális mező hiányzó marad a kimenetben (nem false, nem üres map/lista)"; add: "A property-teszt NEM elég: a Forms-vektorok és a vendorolt fixture az egyetlen független orákulum."

### F8 (should-fix) S5: what Forms actually returns, and a pre-existing missing input
Evidence: Forms go/real_schema_test.go (2f02a75) drives Parse/CompileSchema/Validate/ApplyDefaults only; it does not call Expand/Normalize. Normalize(doc, shape, a, g, ctx) (go/normalize.go) needs a Shape, access keys, Grammar and a Context (Origin/Attestation) and returns a NormalizationResult whose Object is an expanded Node tree with access wrappers plus ValueOrigins/Provenance; JSON conversion needs CanonicalBytes (go/canonical.go:38) or Emit. The test also needs `CIC_REGISTRY_ROOT` = a registry checkout at 6db77d4 and verifies sha256 c9a4d14c... before compiling. So "a kifejtett NetworkSpace objektum" is not a one-liner: the agent must (1) check out the registry at the pin in its clone, (2) assemble Grammar/access keys the way go/*_test.go does, (3) choose a serialization of the expanded tree and decide how authored/default origin and wrappers map to plain config. This is the likeliest place to stall or to hand-write "Forms output". The spec's stop condition ("ha az Expand/Normalize kimenete nem állítható elő") is right but should give the escape: if the expanded wrapper form cannot be reduced to plain values without a new rule, use Denormalize of the result (documented inverse, normalize.go) and say so; do not invent a reduction.
Also: the Go version in the builder image is 1.25.0 (Dockerfile); Forms go.mod requirements not checked here (not verified). Forms pin file lists registry-network-space = general/network/network-space/network-space.yaml, not the oracle-cloud provider file; the spec should state which one the intent is validated against (general).
Change: add the preceding to S5, plus "a golden vektor fájlok a repón kívüli scratch-ben készülnek; a modulba csak a bemásolt adat (nem kód) kerül, a SOURCE.md mintájára (commit, parancs, sha256), és a licenc-döntés a tulajdonosé" (already partially there; make the data-file licence question an explicit owner item: the registry file is CC BY-NC-SA, the vectors derive from an intent authored by the agent, not from the schema text).

### F9 (should-fix) S6 measurement feasibility

The spec's "git archive + tar -x eldobható másolat" is incompatible with `docker compose exec` (it would run on the live mount). Say: use `docker run --rm -v <scratch>:/app <builder image>` (or a unique `-p` project name) and print `docker compose ps`/mount + `git rev-parse HEAD` inside the container as the first measurement line.

Installing one means `go install` from the network and a version choice; module go.mod must not change (use GOFLAGS=-mod=mod in scratch only). - Real Call test: possible and has a pattern (module_loadtest_test.go TestHostLoadExecute builds an inline cic-flow mock with wazero; mock response body is hard-coded `{}` and status 200; the mock is a local closure, not a reusable helper).
