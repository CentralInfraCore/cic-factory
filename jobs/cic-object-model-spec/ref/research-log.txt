    Az aktuális érték közvetlenül a deklaratív YAML inputból származik.

origin: sealed
    CIC/schema által materializált zárt node.
    Ezen a node-on és az alatta levő subtree-n YAML authoring nem megengedett.

És itt a sealed nekem lényegesen pontosabbnak tűnik a template-nél.

Ráadásul ebből kialakul egy nagyon elegáns authoring szabály:

walk(schema-materialized tree, yaml input)

node.origin == sealed
    AND yaml megpróbál belépni
        → reject

node authorable
    AND yaml adott értéket
        → origin = yaml

node authorable
    AND yaml nem adott értéket
    AND schema default létezik
        → origin = schema

Ez már gyakorlatilag önmagában leírja a merge/materialization alapalgoritmus jelentős részét.

1. SPEC.md — ez legyen a Biblia

Nem 100 oldal.

Első verzióban akár 15–25 oldal, de brutálisan normatív.

Első mondatok között:

A CIC object model consists of recursively materialized CIC nodes.

Every CIC node consists of:
- a value,
- an origin,
- zero or more primitives.

Every structured value defined by a CIC schema is recursively
materialized into CIC nodes unless explicitly declared opaque.

Utána a legfontosabb invariánsok.

Például:

INV-001
Every schema-known structured child MUST be represented as a CIC Node.

INV-002
Raw authoring representation MUST NOT cross the module boundary.

INV-003
A module MUST receive only fully resolved, materialized and validated CIC objects.

INV-004
Unknown structured values MUST be rejected unless explicitly declared opaque.

INV-005
No valid CIC node may have undefined primitive semantics.

Ez lesz az egész rendszer gerince.

Na, szerintem ez a megfelelő súly.
